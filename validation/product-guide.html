OpenTrialDesign user guide

library(OpenTrialDesign)

Installation and scope

Install from source with install.packages("OpenTrialDesign_0.1.0.tar.gz", repos = NULL, type = "source"). Optional engines can be installed with install.packages(c("gsDesign", "rpact", "simsurv")); the interface requires shiny, and reporting requires rmarkdown plus Pandoc. PDF additionally requires a working LaTeX installation. The package core does not depend on Shiny.

The first release supports equal-allocation, two-arm superiority calculations, canonical one-sided sequential designs, a specific two-stage adaptive inverse-normal procedure, and exponential proportional hazards survival trials. Noninferiority, equivalence, cluster trials, recurrent events, competing risks, and nonproportional hazards are outside these adapters’ present scope. Such analyses require an appropriate validated engine and explicit estimand.

Monte Carlo operating characteristics

Analytical power differs from a Monte Carlo estimate. Each simulation result contains the rejection count, replication count, seed, estimate, plug-in MCSE sqrt(p_hat * (1-p_hat) / B), and exact Clopper-Pearson 95% interval. A zero MCSE at zero observed rejections does not imply absence of uncertainty; use the interval. Expected enrollment, information, event-count and duration summaries include approximate t-based Monte Carlo intervals. Stopping and target-attainment probabilities use marginal exact binomial intervals; they do not have simultaneous 95% coverage. Choose replication counts for the precision required: at true error 0.025, 1000 replications give an approximate MCSE of 0.00494.

The equality null uses treatment effect zero, not the planning alternative. The normal test is the pooled t test. The binary analysis is prop.test with no continuity correction. All-zero or all-one binary samples cannot reject equality and are assigned p=1. Discreteness can affect nominal type I error. The equality null alone does not establish uniform control across all nuisance parameters. Broader null grids and multiplicity control are study-specific work.

Sequential alpha is the one-sided upper efficacy error. A lower futility crossing does not reject the null. For gsDesign, no-futility uses test.type=1, binding beta-spending uses 3, and nonbinding beta-spending uses 4. Beta spending is Hwang-Shih-DeCani with gamma=-2. Nonbinding upper boundaries protect alpha if futility is ignored; power and expected information depend on whether futility is followed. The canonical simulator can evaluate that distinction, and refuses to ignore a binding rule. Analytical gsProbability enforces lower stopping even for a design calibrated with nonbinding futility.

Information fractions are prespecified. The canonical simulation is a Brownian independent-increments experiment, not patient-level evidence for arbitrary endpoints or data-dependent information times. theta is canonical drift; the default analytical alternative is the native design’s drift. Information is normalized to fixed-design information, not a patient count.

The rpact adapter returns its own native object. Engine-specific OF and Pocock spending approximations are retained. Never transfer boundaries, power values, or information scales between engines without an explicit compatibility check.

This workflow uses rpact’s getDesignInverseNormal and getSimulationMeans with native conditional-power recalculation. The combination weights are fixed by the originally planned information fractions. Stage-one enrollment is total across both arms, and stage-two limits are additional enrollment across both arms. Native normal-approximation recalculations can yield fractional effective sample sizes; these simulations are not an integer operational enrollment rule. Independent normally distributed stage observations, equal allocation, and the rpact normal approximation are assumed. Null and alternative scenarios are always reported. There is no futility boundary in this adapter. The procedure does not authorize changing an ordinary pooled-test design after observing an unblinded effect. Confirmatory use requires protocol-specific review of combination weights, independent stage p-values and the adaptation rule; a finite Monte Carlo experiment alone does not prove error control.

The estimand is the treatment/control hazard ratio. Planning supports HR below one as benefit. The Schoenfeld approximation supplies the event target, and rpact translates that target into enrollment under uniform accrual, exponential survival, equal allocation and independent dropout. The returned native sizes are unrounded planning quantities; round enrollment and event targets upward when specifying an operational trial, then assess the resulting operating characteristics with the simulation API. No precision claim is made for unmodeled recruitment patterns or nonproportional hazards.

Simulation uses simsurv event times, independent exponential dropout and administrative censoring. All durations use one common unit. dropout is a probability by dropout_time, not a hazard. The logrank signed treatment observed-minus-expected score supports benefit when negative. The p-value is lower-tail one-sided. If an event target is supplied, the trial stops at that calendar event or the administrative cap, whichever comes first. The result reports target attainment; it never assumes an unreachable event target was met. Participants not recruited by early stopping do not enter the analysis.

Example library and scientific verification

The installed examples/catalog.csv documents 30 independently executable scenarios; installed examples/ASSUMPTIONS.md explains each rationale and limits the synthetic effects to teaching/planning demonstrations. They are accessible through run_example("TD-001") and standalone scripts. The supplied repository contained no external plan defining TD IDs. This version defines its own explicit product catalog; equivalence to that missing external specification is not claimed.

Numerical reference checks compare normal/binary calculations directly to stats, sequential spending and power to engine integration, and survival events to the Schoenfeld expression. These verify adapter behavior, not independent validation of their engines. Monte Carlo checks use prespecified seeds and tolerances scaled to sampling error. A reference expectation is never replaced with a simulated point estimate merely to obtain passing tests.

See repository validation/ for actual execution logs and docs/PHASE-STATUS.md for limitations. No result should be described as scientifically validated solely because a function returned successfully. rpact installation qualification for GxP environments is separate and has not been performed here.

Projects freeze all default parameters and record schema and software versions. write_project(project, "design.json") saves non-executable JSON. execute_project(read_project("design.json")) replays it through the same core. Schema validation rejects unknown workflows, arguments, code-like numeric values and unsupported versions. Scientific input validation occurs in the engine when executed. JSON is configuration data; no R expressions from an import are evaluated. Only trusted local archival RDS files should be loaded by the user outside the application.

Supported workflows are fixed_sample_size, fixed_power, fixed_simulation, sequential_design, sequential_means, adaptive_simulation, survival_design and survival_simulation. Fixed workflows take trial_spec parameters plus sample size and simulation settings as applicable. Other workflows take the corresponding public function’s parameters.

This positive-mean, one-sided, equal-allocation workflow uses rpact’s native t-approximation planning and power functions. Cumulative per-arm stage sizes are rounded upward, the information fractions recomputed, and spending boundaries recalibrated in rpact. The maximum size is increased if recalculated power falls below target. Final output includes integer stage counts, realized information and achieved analytical power. No gsDesign boundaries or fixed stats t-test calculations are combined with this procedure.

Background jobs and reproducibility exports

start_simulation(project) starts an isolated process for a fixed, adaptive or survival simulation project. simulation_status(job) is nonblocking; collect_simulation(job) requires successful completion. cancel_simulation(job) terminates an active worker and never returns a partial estimate as a completed run. The application allows one active job per session and remains interactive while it runs. Closing the session cancels its worker. API users can choose larger runs than the application’s 100,000-replication limit.

result_table(result) provides spreadsheet data. export_bundle(result, "trial.zip", include_report = FALSE) writes CSV, assumptions, provenance, session information, the exact result, the replay project when present and MD5 integrity checks. MD5 checks detect accidental changes, not authenticity. Use the Projects and exports tab to save JSON, CSV and ZIP, and Scientific reporting for HTML/PDF. The full guide is downloadable from the application.

See the repository deployment guide for local, container and batch commands. The version-1 example catalog is now explicitly defined by the installed catalog and per-example rationales. It does not claim equivalence to an absent external project plan. These workflows support planning and simulation within the stated assumptions; they do not confer protocol-specific qualification.
